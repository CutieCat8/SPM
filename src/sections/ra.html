เสริม 1 · Requirements Analysis

การวิเคราะห์ความต้องการ = การศึกษาแนวทางหรือการดำเนินงาน เพื่อนำข้อมูลที่สกัดไปใช้ในการออกแบบและพัฒนาซอฟต์แวร์

บทบาท SA (System Analyst / นักวิเคราะห์ระบบ): สกัดความต้องการ → วิเคราะห์ → ออกแบบระบบ → ส่งต่อทีมพัฒนา → จัดทำเอกสารด้านซอฟต์แวร์
ความสามารถที่ต้องมี: ความรู้ด้านเทคนิค · ทักษะการวิเคราะห์ · การสื่อสาร · การจัดการ

UR → URS → SRS

เริ่มจากถามว่า "ใครใช้ระบบบ้าง?" แล้วแจกแจงความต้องการตามกลุ่มผู้ใช้ด้วยคำถาม

  • Who — บทบาทของผู้ใช้ เช่น ผู้ปฏิบัติงาน หัวหน้า ผู้ดูแลระบบ
  • What — สิ่งที่ผู้ใช้จะทำกับระบบ หรือคาดหวังให้ระบบทำอะไร
  • How — ผู้ใช้อยากให้ระบบทำอย่างไร หรือทำไมอยากใช้ระบบ เพื่ออะไร
ตัวอย่างการเขียนที่ต้องทำเป็น (มักออกเป็นข้อเขียน)

URS = จัดกลุ่มความต้องการ หรือจัดทำเป็นโมดูล

URS-01 ผู้ใช้สามารถเข้าใช้งานด้วยการลงชื่อเข้าใช้ (Login) ตามระดับสิทธิ์การใช้งาน ได้แก่ ผู้ปฏิบัติงาน, หัวหน้า, ผู้ดูแลระบบ

SRS = ระบุฟังก์ชันงานของซอฟต์แวร์ ให้บรรลุความต้องการของผู้ใช้ ประกอบด้วย System Functional · Operational Constraint · Services

SRS-01 ระบบสามารถรองรับการ login ได้ด้วย username และ password
SRS-02 ระบบสามารถตรวจสอบระดับสิทธิ์ผู้ใช้งานที่ login ได้ดังนี้ ผู้ปฏิบัติงาน, หัวหน้า, ผู้ดูแลระบบ

โครงสร้างคือ 1 URS มีได้หลาย SRS อยู่ข้างใต้ — URS ขึ้นต้นด้วย "ผู้ใช้/หัวหน้า/แอดมิน สามารถ…" ส่วน SRS ขึ้นต้นด้วย "ระบบสามารถ…"

เสริม 2 · Analysis Model & UML

แบบจำลอง (Model) = แผนภาพที่แสดงข้อเท็จจริงหรือกิจกรรมที่เกิดขึ้นในระบบ ด้วยการใช้สัญลักษณ์แทนการอธิบายด้วยตัวหนังสือ ซึ่งชัดเจน เข้าใจง่าย และไม่ซับซ้อน
แบบจำลองการวิเคราะห์ = แบบจำลองที่เขียนขึ้นจากข้อกำหนดความต้องการของระบบ สะท้อนหน้าที่การทำงานของระบบ และนำไปใช้ออกแบบต่อ
1. Behavioral UML Diagram
เชิงลักษณะการทำงาน
  • Activity Diagram
  • Use Case Diagram
  • Sequence Diagram
2. Structural UML Diagram
เชิงโครงสร้าง
  • Class Diagram
  • Entity Relationship Diagram
  • Data-flow Diagram

นิยามสั้นที่ต้องท่องได้:
Use Case Diagram — แผนภาพที่ใช้แสดงปฏิสัมพันธ์ระหว่างระบบงานภายในและผู้ใช้งาน
Activity Diagram — แผนภาพการทำงานของระบบ แสดงขั้นตอนและเงื่อนไขการทำงานแต่ละงาน
Sequence Diagram — แผนภาพแสดงปฏิสัมพันธ์ระหว่าง Object โดยเฉพาะการส่ง Message ตามลำดับเวลา

วงรี		ฟังก์ชันงานหรือกระบวนงาน — มักขึ้นต้นด้วยคำกริยา
System
กรอบสี่เหลี่ยม		แสดงขอบเขตของ Use case
Packageแสดงการจัดกลุ่ม Use case เข้าด้วยกัน มีประโยชน์มากเมื่อแผนภาพซับซ้อน เป็นองค์ประกอบที่ละเว้นได้
Association
เส้น / ลูกศรประ		ความสัมพันธ์ระหว่าง Actor กับ Use case และระหว่าง Use case ด้วยกัน เช่น include/uses, extends
include vs extend — ถามแทบทุกครั้ง

<<include>> / uses : The use case is mandatory — ตัวที่ถูก include คือสิ่งที่ต้องเกิดเสมอ
<<extend>> : The use case is optional — scenario สมบูรณ์ได้แม้ไม่มี use case ที่ extend มา
ตัวอย่างจากสไลด์: "จองที่จอดรถ" <<include>> "ออก QR ที่จอด" (ต้องออกเสมอ) / "จ่ายค่าที่จอด" <<extend>> "ใช้ส่วนลด/คูปอง" (จะใช้หรือไม่ใช้ก็ได้)

รูปแบบ Activity Diagram 5 แบบ

#รูปแบบลักษณะการทำงาน
1Sequenceการทำงานตามลำดับ เขียนเป็นลำดับขั้นตอนการทำงาน
2Selectionเลือกกระทำตามเงื่อนไข มี 2 กระบวนการ: จริงทำอย่างหนึ่ง เท็จทำอีกอย่างหนึ่ง
3Iterationการทำซ้ำ วน Loop ในขั้นตอนเดิมจนกว่าจะเป็นไปตามเงื่อนไข
4Do whileตรวจสอบเงื่อนไขก่อน ถ้าจริงจึงทำตามคำสั่ง แล้ววนกลับจนกว่าเงื่อนไขเป็นเท็จ
5Do untilทำคำสั่งก่อน 1 ครั้ง แล้วตรวจสอบเงื่อนไข ถ้าเท็จกลับไปทำซ้ำจนกว่าเงื่อนไขเป็นจริง
จุดต่างของ Do while กับ Do until

ลำดับ: Do while ตรวจก่อน–ทำทีหลัง (อาจไม่ได้ทำเลย) · Do until ทำก่อน–ตรวจทีหลัง (ทำอย่างน้อย 1 ครั้งแน่นอน)
เงื่อนไขออกจาก loop: Do while ออกเมื่อเท็จ · Do until ออกเมื่อจริง
